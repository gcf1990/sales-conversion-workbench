# 销售转化工作台前端 Demo 设计

日期：2026-06-10

## 1. 项目定位

本项目是一个全新的“销售转化工作台”，不复用旧六量七率工作台的标签体系、脚本、页面结构或 JSON 数据结构。

第一阶段目标是先产出一版前端可视化 Demo，用于确认业务分析动线、页面结构和下钻体验。前端确认后，再接入真实观远数据和明细打标结果。

## 2. 第一阶段范围

第一阶段采用“字段对齐 Demo”：

- 前端页面使用样例数据。
- 样例字段命名尽量对齐后续观远真实数据集。
- 暂不接真实观远接口。
- 暂不接真实 IP 电话明细、试驾录音明细和 LLM 打标结果。
- 第三层问题分布、顾问排行和明细证据先用样例数据模拟真实体验。

后续可接入的第一层漏斗数据集：

- 数据集名称：`[缓存][三品牌]新零售门店级每日全量指标宽表&ads_sale_mart_new_sale_store_lvl_day_exnorm_comb_wms_his`
- 数据集 ID：`e477e5d5aa4664fadb3a7ec7`

## 3. 用户分析动线

业务用户进入工作台后，默认先看到销售环节问题最严重的门店清单，以及这些门店的整体转化表现。

推荐动线：

1. 首页先定位问题门店。
2. 点击某个门店进入门店诊断。
3. 门店诊断按三层结构展开：核心环节 -> 过程指标 -> 明细问题诊断。
4. 在第三层先看问题类型分布，再下钻到顾问，再下钻到 IP 电话或试驾接待明细。

## 4. 首页设计

首页定位不是传统大屏，而是“问题门店工作台”。

### 4.1 顶部销售转化漏斗

漏斗保留四个核心环节：

```text
线索 -> 到店 -> 试驾 -> 订单
```

后续字段对齐：

| 页面指标 | 观远字段 | 说明 |
|---|---|---|
| 线索 | `today_indpdt_leads_cnt` | 独立线索数 |
| 到店 | `today_fst_touch_pflow_cnt` | 首触到店 |
| 试驾 | `today_fst_touch_trial_cnt` | 首触试驾 |
| 订单 | `today_fst_touch_order_cnt` | 首触订单 |

### 4.2 问题最严重门店清单

门店主榜按“综合严重度”排序。

综合严重度第一版只由结构化指标生成，不纳入 LLM 明细质检结果。明细质检稳定后，再把问题集中度、严重问题占比、顾问问题覆盖面纳入评分。

主榜展示字段：

| 字段 | 说明 |
|---|---|
| 门店 | 门店简称 |
| 主要问题环节 | 邀约阶段 / 转化阶段 |
| 综合严重度 | 用于排序 |
| 线索到店率 | 线索到店转化表现 |
| 30s 以下线索占比 | IP 电话质量问题信号 |
| 试驾订单率 | 试驾后转订单表现 |
| 预计影响规模 | 单独展示，不参与主榜排序 |

影响规模单独展示，不直接决定主榜排序，避免大门店天然霸榜。

## 5. 门店诊断页三层结构

门店诊断页采用固定三层下钻结构。

### 5.1 第一层：核心销售环节

第一层展示四个环节：

```text
线索 / 到店 / 试驾 / 订单
```

第一层用于让业务理解当前门店的问题发生在哪一段链路。

### 5.2 第二层：关键过程指标

第二层第一版保留三个关键指标：

| 第二层指标 | 业务含义 | 点击后第三层诊断对象 |
|---|---|---|
| 30s 以下线索占比 | 线索电话沟通质量不足 | IP 电话邀约问题 |
| 线索到店率 | 线索是否被有效邀约到店 | IP 电话邀约问题 |
| 试驾订单率 | 试驾后是否有效转订单 | 试驾接待问题 |

### 5.3 第三层：问题诊断

第三层根据第二层点击指标切换诊断对象：

- 点击 `30s 以下线索占比`：展示 IP 电话邀约问题。
- 点击 `线索到店率`：展示 IP 电话邀约问题。
- 点击 `试驾订单率`：展示试驾接待问题。

第三层固定采用三段式：

```text
问题类型分布 -> 顾问下钻 -> 明细证据
```

## 6. 问题类型体系

IP 电话和试驾接待共用同一套问题类型，只是数据来源不同。

| 问题类型 | 核心定义 |
|---|---|
| 客户需求识别不足 | 顾问没有先弄清客户真实购车动机、预算、用途、周期、决策人、对比车型，就开始介绍、报价或邀约 |
| 产品价值转化不足 | 顾问讲了功能、配置、参数，但没有讲清这些内容对客户有什么实际好处 |
| 版本价格推荐不清 | 客户问低配、中配、高配、优惠、落地、分期时，顾问没有帮客户判断哪个版本最适合 |
| 顾虑异议承接不足 | 客户表达担心、拒绝、犹豫、质疑时，顾问没有正面接住并化解 |
| 竞品对比引导不足 | 客户提到其他品牌、车型、网上评价时，顾问没有建立清晰对比逻辑 |
| 下一步推进锁定不足 | 顾问没有把当前沟通推进到明确下一步动作，导致客户热度流失 |

数据来源：

| 诊断对象 | 数据来源 |
|---|---|
| IP 电话邀约问题 | IP 电话文本 |
| 试驾接待问题 | 试驾录音文本 |

## 7. 明细打标规则

一条 IP 电话明细或一次试驾接待明细可以命中多个问题类型。

建议样例数据结构：

| 字段 | 用法 |
|---|---|
| `issue_tags` | 多个命中问题类型 |
| `primary_issue` | 主问题类型，用于顾问排行和默认聚合 |
| `evidence_text` | 电话或试驾文本里的关键证据片段 |
| `advisor_name` | 顾问 |
| `customer_id` | 客户标识，Demo 可匿名 |
| `scenario` | `ip_call` 或 `test_drive` |
| `suggestion` | 改进建议 |

第三层页面中，问题分布按 `issue_tags` 统计，顾问排行可按 `primary_issue` 和命中明细数排序。

## 8. 前端 Demo 页面结构

### 8.1 首页

首页建议包含：

- 顶部筛选：日期、品牌、车系、大区、小区、门店。
- 漏斗概览：线索、到店、试驾、订单。
- 问题门店榜：按综合严重度排序。
- 门店概况卡：展示选中门店的主要短板、影响规模、建议优先动作。

### 8.2 门店诊断页

门店诊断页建议包含：

- 门店基础信息和核心结论。
- 第一层核心环节：线索、到店、试驾、订单。
- 第二层过程指标：30s 以下线索占比、线索到店率、试驾订单率。
- 第三层问题诊断：问题类型分布、顾问排行、明细证据。

### 8.3 明细证据区

明细证据区建议展示：

- 顾问。
- 客户标识。
- 沟通场景。
- 命中问题标签。
- 关键证据片段。
- 建议动作。

## 9. 第一版验收标准

前端 Demo 第一版验收标准：

1. 首页能清楚表达“先找问题最严重门店”的工作方式。
2. 门店诊断能按三层结构完成点击下钻。
3. 点击不同第二层指标时，第三层能在 IP 电话邀约问题和试驾接待问题之间切换。
4. 第三层能展示 6 类问题分布、顾问排行和明细证据。
5. Demo 数据字段与后续观远数据集字段命名保持基本可映射。

## 10. 后续迭代边界

前端 Demo 确认后，再进入真实数据接入阶段。

后续阶段包括：

- 接入观远聚合指标数据。
- 接入 IP 电话文本明细。
- 接入试驾录音文本明细。
- 建立 LLM 问题打标流程。
- 将明细问题集中度纳入综合严重度评分。
